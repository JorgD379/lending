# Переезд сайта lab-itis.ru на собственный VPS + бэкенд для заявок

Дата: 2026-07-13
Статус: согласовано с пользователем, готово к написанию плана реализации

## Контекст

Сайт lab-itis.ru — статический лендинг (GitHub Pages), 41 HTML-страница,
контент отраслей/задач/процессов хранится в одном файле `js/data.js`
(~9000 строк). Формы на сайте изначально никуда не отправляли данные —
это было исправлено в отдельной сессии (см. `server/` — Node/Express
сервис `POST /api/lead`, отправляет письмо через SMTP-релей Яндекс 360 на
info@lab-itis.ru, задуман для отдельного поддомена `api.lab-itis.ru`).

Пользователь решил полностью перенести сайт на свой VPS (самый дешёвый
доступный тариф) вместо GitHub Pages, и хочет заодно:
- нормальный бэкенд для форм (уже есть, но требует адаптации под то, что
  теперь всё на одном сервере — уходит нужда в отдельном поддомене/CORS);
- хранить заявки в базе и смотреть их в простой панели (мини-CRM), а не
  только в почте;
- задел на будущее для возможного визуального редактора контента, но
  **не сейчас** — контент правится примерно раз в неделю и продолжит
  править ся через код (разработчиком/Claude), это осознанное решение
  пользователя после обсуждения trade-off'ов.

## Цели первого этапа (phase 1 — этот документ)

1. Сайт и API работают с одного дешёвого VPS, без GitHub Pages.
2. Все формы на сайте реально отправляют заявки (email + запись в БД).
3. Заявки не теряются, даже если email временно не уходит.
4. Есть защищённая панель для просмотра/поиска/статусов заявок.
5. Базовая SEO-гигиена (sitemap.xml, robots.txt) и производительность
   (сжатие, кэш-заголовки) — дёшево и без architectural overhead.
6. Архитектура не мешает добавить визуальный редактор контента позже.

## Явно вне рамок этого этапа (future work)

- Полноценная CMS / визуальный редактор контента (блог, отрасли, кейсы).
  Пользователь рассмотрит эту идею позже; в разделе "Задел на будущее"
  ниже описано, что для этого потребуется, чтобы не переделывать
  архитектуру, когда до этого дойдёт очередь.
- Перевод страниц `/industry/` и `/subindustry/` с клиентского рендеринга
  (JS читает `data.js` по `?id=`) на серверный рендеринг для SEO. Это
  отдельная фронтенд-задача, зафиксирована как известное ограничение.
- Многопользовательские роли в админ-панели (сейчас — один общий логин).
- Уведомления/интеграции с мессенджерами из панели заявок.

## Архитектура

### Хостинг и сеть

- Один VPS (Ubuntu, самый дешёвый тариф — 1 vCPU / 1GB RAM достаточно
  для nginx + статики + одного Node-процесса + SQLite при текущей
  нагрузке лендинга).
- DNS: A-записи `lab-itis.ru` и `www.lab-itis.ru` указывают напрямую на
  IP VPS (вместо текущих записей на GitHub Pages). Файл `CNAME` в корне
  репозитория (артефакт GitHub Pages custom domain) удаляется.
- nginx — единственная точка входа на 80/443:
  - раздаёт статику сайта напрямую из папки с кодом (`git clone` этого
    репозитория на сервере);
  - проксирует `/api/*` в Node-процесс на `127.0.0.1:3001`;
  - TLS через certbot на оба домена (`lab-itis.ru`, `www.lab-itis.ru`,
    редирект www → apex или наоборот — на выбор при деплое);
  - gzip/brotli, HTTP/2, кэш-заголовки: длинные для `/assets/*` (шрифты,
    картинки — не меняются), короткие/no-cache для HTML (правки контента
    должны быть видны сразу, не раз в неделю кэшировано);
  - `/data/`, `/uploads/`, файлы SQLite и любые пути самого бэкенд-сервиса
    **не** отдаются nginx как статика — доступ к вложениям заявок только
    через авторизованный роут API.

### Бэкенд-сервис

Расширение уже существующего `server/` (было рассчитано на отдельный
поддомен `api.lab-itis.ru` с CORS; теперь всё на одном домене — CORS
между фронтом и бэком больше не нужен, `LEAD_API_URL` на фронте
становится относительным `/api/lead`).

Структура:
```
server/
  src/
    app.js            — сборка Express-приложения, миддлвары
    db.js              — инициализация SQLite (better-sqlite3), схема
    routes/
      lead.js          — POST /api/lead (приём заявок, публичный)
      admin.js          — GET/POST /api/admin/* (панель, требует логина)
    lib/
      mailer.js        — обёртка над nodemailer (уже есть логика,
                          переносится сюда как модуль)
      auth.js           — хэш пароля, сессии, rate-limit логина
  data/
    leads.db           — файл SQLite (гитигнор)
  uploads/
    <lead-id>/<file>   — прикреплённые файлы (гитигнор)
  server.js             — точка входа, поднимает app.js
```

### Данные заявки (таблица `leads`, SQLite)

| Колонка              | Тип     | Комментарий                                   |
|-----------------------|---------|------------------------------------------------|
| id                    | INTEGER | primary key, autoincrement                     |
| created_at            | TEXT    | ISO timestamp                                   |
| source                | TEXT    | modal-simple / modal-complex / home-form / contacts |
| name                  | TEXT    |                                                  |
| email                 | TEXT    | nullable                                        |
| phone                 | TEXT    | nullable                                        |
| company               | TEXT    | nullable                                        |
| industry              | TEXT    | nullable                                        |
| message               | TEXT    | nullable                                        |
| consent               | INTEGER | 0/1                                              |
| marketing             | INTEGER | 0/1                                              |
| attachment_path       | TEXT    | nullable, относительный путь в uploads/         |
| ip                     | TEXT    | для антиспам-аудита                             |
| status                 | TEXT    | new / in_progress / won / lost (default: new)   |
| email_sent            | INTEGER | 0/1 — доставлено ли письмо                      |
| email_error           | TEXT    | nullable — текст последней ошибки отправки       |

### Надёжность приёма заявок

Текущая логика (`POST /api/lead`) отправляет письмо и всё. Меняется
порядок обработки:

1. Валидация полей (как сейчас: имя + email-или-телефон, согласие).
2. Honeypot-проверка (как сейчас) — если бот, отвечаем `{ok:true}`, в БД
   не пишем.
3. **Запись в SQLite первой** — практически не может отказать.
4. Попытка отправить письмо. Если успех — `email_sent=1`. Если ошибка —
   `email_sent=0`, `email_error` = текст ошибки, но пользователю сайта
   всё равно отвечаем `{ok:true}` (заявка сохранена, ничего не потеряно).
5. В админ-панели заявки с `email_sent=0` помечены визуально, есть кнопка
   «отправить письмо повторно» (вызывает переотправку по этой же записи).

### Админ-панель

- Доступ: `https://lab-itis.ru/admin/` (обычный путь на том же домене,
  не поддомен).
- Один общий логин/пароль (без ролей и многопользовательности — не
  нужно на этом этапе). Пароль хранится как bcrypt-хэш в `.env` сервера
  (не в БД, чтобы не плодить сущности ради одного пользователя).
- Сессия — cookie с флагами `httpOnly` и `secure` (только HTTPS).
- Отдельный, более строгий rate-limit на роут логина (например 5 попыток
  / 15 минут с одного IP) — защита от перебора пароля.
- Экран «Список заявок»: таблица (дата, источник, имя, контакт, статус,
  фрагмент сообщения), фильтры по статусу/источнику/дате, поиск по
  имени/email/телефону/компании.
- Экран/раскрытие «Карточка заявки»: полный текст, вложение (скачивание
  через авторизованный роут), смена статуса, пометка о недоставленном
  письме + повторная отправка.

### Безопасность (сводно)

- HTTPS everywhere (certbot), `httpOnly`+`secure` cookies для сессии.
- bcrypt для пароля админки, отдельный rate-limit на логин.
- Вложения заявок недоступны по прямой публичной ссылке — только через
  авторизованный API-роут.
- На уровне VPS: файрвол (открыты только 80/443/22), вход по SSH только
  по ключу, автообновления безопасности ОС.
- Бэкапы: ежедневная копия `leads.db` + `uploads/` за пределы VPS
  (например в объектное хранилище или на другой сервер) — cron-задача,
  описывается в плане реализации.
- Юридический нюанс (152-ФЗ, хранение персональных данных) — у сайта уже
  есть форма согласия и политика конфиденциальности; хранение на своём
  VPS в РФ не создаёт новых юридических рисков относительно текущей
  схемы (email на info@lab-itis.ru), но это не юридическая консультация —
  при необходимости формальной строгости сверить с профильным юристом.

### SEO и производительность

- Добавить `robots.txt` и `sitemap.xml` (по текущему списку страниц;
  обновление вручную или маленьким скриптом при добавлении страниц —
  описать в README деплоя).
- nginx: gzip/brotli, HTTP/2, кэш-заголовки (долгие для `/assets/*`,
  короткие/no-cache для HTML — контент правится еженедельно, важно не
  показывать посетителям устаревшую закэшированную версию).
- Известное ограничение (не чинится в рамках этого этапа): страницы
  `/industry/` и `/subindustry/` рендерят контент на клиенте из
  `js/data.js` по query-параметру — поисковые боты могут не видеть
  контент конкретной отрасли при первом заходе. Фиксируется как future
  work, требует отдельной фронтенд-переработки (например, статическая
  генерация одной HTML-страницы на отрасль).

### Деплой и обновление

- На VPS — обычный `git clone` этого репозитория.
- Обновление статики: `git pull` (nginx ничего перезапускать не нужно).
- Обновление бэкенда: `git pull` + `systemctl restart <сервис>`.
- Подробные шаги (nginx-конфиг, systemd unit, certbot, первичная
  настройка SQLite) — в `server/README.md`, обновляется в рамках плана
  реализации под однодоменную схему (сейчас README ориентирован на
  отдельный поддомен `api.lab-itis.ru` — это меняется).

## Задел на будущее (не реализуется сейчас)

Если позже понадобится визуальный редактор контента:
- Данные отраслей/задач/процессов переносятся из `js/data.js` в ту же
  SQLite (ещё одна таблица), либо в JSON-файлы, читаемые бэкендом.
- Пишутся CRUD-роуты по аналогии с `routes/admin.js` для заявок.
- Простая форма редактирования в той же admin-панели.
- Инфраструктура (nginx, Node-процесс, SQLite, деплой через git) уже
  готова — это расширение, а не переделка.

## Тестирование и проверка (план для этапа реализации)

- Юнит/интеграционные проверки `routes/lead.js`: запись в БД происходит
  до отправки письма; ошибка отправки письма не роняет запрос и не
  теряет заявку.
- Проверка `routes/admin.js`: без сессии — 401/редирект на логин; после
  логина — доступ; rate-limit логина отрабатывает.
- Ручная проверка на реальном VPS после деплоя: все 4 формы сайта
  (обе модалки, главная, контакты) отправляют заявку → она появляется и
  в письме, и в панели.
- Проверка `robots.txt`/`sitemap.xml` доступны и валидны.
- Проверка кэш-заголовков и сжатия через `curl -I`.
